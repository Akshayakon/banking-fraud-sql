# Banking Fraud & Transaction Analysis (SQL)

A small project that finds fraud in PaySim-style transactions using SQL window functions.
It uses only Python 3 and its built-in SQLite, so there is nothing to install.

> **Note:** the data is synthetic. It is generated by `generate_data.py` in PaySim's column format, and it is not real PaySim output or real bank data.

```
python run.py      # generates fraud.db on first run, then runs every analysis
```

## Files
| File | Purpose |
|---|---|
| `generate_data.py` | Builds ~50k synthetic transactions (PaySim columns) and injects 3 fraud patterns |
| `sql/01_schema.sql` | Table definition |
| `sql/02_anomalies.sql` | Individual detection queries: `SUM OVER`, `LAG`, `LEAD`, rolling `AVG` |
| `sql/03_risk_score.sql` | Combines the rules into a view, then measures precision and recall |
| `sql/04_indexes.sql` | Composite and partial indexes |
| `run.py` | Runs everything and prints a before/after index benchmark |

## Techniques
- **Running totals:** `SUM(amount) OVER (PARTITION BY account ORDER BY step)`.
- **Velocity:** `step - LAG(step, 2)` finds 3 transactions in about an hour.
- **Spike detection:** `AVG(...) OVER (... ROWS BETWEEN UNBOUNDED PRECEDING AND 1 PRECEDING)` compares each amount to the account's own history, excluding the current row.
- **Mule pattern:** `LEAD` over a per-account event stream finds a TRANSFER in followed by a same-amount CASH_OUT.
- **Account drain:** a balance check on `old_bal_orig > 0 AND new_bal_orig = 0`.
- **Evaluation:** the rule flags are scored against the `is_fraud` label.

## Sample results (seeded, so reproducible)
- About 95% precision and 70% recall from three simple rules. The cash-out leg of the mule pattern has no velocity or spike signal, so it is missed.
- The composite index `(name_orig, step, txn_id)` removes the sort step: the per-account lookup went from 10 ms to 1.3 ms, and the window-function scan from 104 ms to 65 ms.

## Limitations
- The rules are simple and hand-tuned against injected patterns. Real fraud is messier, and the 95% precision shown here would not carry over to real data.
- Recall is about 70%: the mule's cash-out leg has no velocity or spike signal.
- SQLite is used for portability. The same window-function SQL works on PostgreSQL and SQL Server with minor syntax changes.

## Using the real data
Load PaySim's CSV into `transactions`, mapping `nameOrig`→`name_orig`, `oldbalanceOrg`→`old_bal_orig`, and so on. The SQL needs no changes. The Kaggle credit-card dataset works too, with `Time` as `step` and a card ID as the partition key.
